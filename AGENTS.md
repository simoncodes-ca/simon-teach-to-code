# AGENTS.md

Teaching scaffolds that an 11-year-old fills in to learn programming. Each numbered folder is one project: a finished, good-looking web page whose JavaScript is deliberately unfinished.

## The rule that overrides everything

**The stubs are the deliverable. Leave them unwritten.**

Every project ships a `.js` file whose core functions are empty, marked `// TODO`, and wrapped in graduated hints. Filling them in is the entire point of the repo — it is the learner's work, and completing it destroys the product.

So when a request sounds like "make the game work", "fix the elevator", or "the calculator returns nothing", the job is almost always to improve the *scaffold* — sharper hints, a stub reordered, a bug in the given wiring, a stub whose completion produces no visible change. Implement a stub only when the user says so in as many words.

To test that a scaffold is completable, fill the stubs in a throwaway copy or at runtime via `page.evaluate` — never in the tracked file.

## Project anatomy

Every `NN-name/` folder holds the same seven things:

| File | Role |
|---|---|
| `NN.html` | The page. Finished — every id and hook the implementation needs is already there |
| `styles.css` | The look. Finished |
| `NN.js` | **The scaffold.** Memory, then stubs, then given wiring |
| `README.md` | The learner's guide: concepts, vocabulary, what the wiring already does |
| `PRODUCT.md` | The product contract — scope, constraints, what is deliberately deferred |
| `DESIGN.md` | The visual system, recorded from the built page (absent for 02) |
| `assets/` | Images, fonts, sounds — all local, all relative paths |

Projects 18 to 22 add a test file, `NN.test.ts`. See **Tests** below.

Project 15 adds `server.js`, a second program that runs in a terminal, and `scores.json`, the list it keeps on disk. Its stubs are split across two files, and each file carries its own answer key.

Project 16 splits its stubs across `tank.js` and `shells.js`, among six script files. Each of the two carries its own answer key.

Project 9 adds `phaser.min.js`, vendored next to the HTML. A library a project's `PRODUCT.md` names lives in the folder as a file like any other, never behind a package manager, until project 17.

Project 17 adds `package.json`, `package-lock.json`, `tsconfig.json` and `vite.config.ts`, and takes Phaser from npm. Its stubs are types, so its payoff is the type-error count that `vite-plugin-checker` shows in the terminal and on the page. `node_modules/` is never committed.

Project 20 keeps project 19's shape. Its `maps/` adds `horseshoe.json` to project 19's two. Its stubs are all in `paths.ts`, which imports only `terrain.ts` and `map.ts`. `units.ts` there is finished: project 19's answers, with tanks that follow a route.

Project 21 keeps project 20's shape, and is the first project to add a line to `terrain.ts`: a seventh ground, `ore`, and a `holds` column saying how much ore one fresh cell of a ground starts with. From project 17 the scaffold is `NN.ts`, not `NN.js`, and a project may span several files. The sections below still apply, one set per file.

The scaffold file is organised in numbered sections: **the memory** (the handful of variables that hold all state), **your job** (the stubs), **the given wiring** (rendering, event handlers, setup). The learner is told to read the wiring but not edit it.

Two projects break this shape on purpose, and `ROADMAP.md` records why:

- **Project 14** splits a finished game into several files. It has no stubs at all — the split is the lesson.
- **Project 17** rewrites a finished game in TypeScript. Its stubs are type annotations, not function bodies.

## Writing a stub

- **Two hints at the stub**, in this order: `Gentle hint:` names the idea, `Stronger hint:` names the method. The answer never sits next to the stub.
- **The answer lives in the answer key at the bottom of the file**, so it is there when the learner wants it but out of sight while they work. The stub's last hint line points to it: `Stuck? The answer key is at the bottom of this file.`
- **Order stubs so each one only needs what came before it.** The function that assembles the others goes last.
- **Every completed stub changes something on screen.** A stub whose payoff is invisible is a defect — check that the given wiring actually reads its return value.
- **Every function the learner must call is named in a comment.** A helper sitting in the wiring that nothing points at is unguessable.
- Plain language, no jargon. Repetition the learner can follow beats indirection they cannot.

Read the project's `PRODUCT.md` before changing scope — it records what is deliberately deferred, and "missing" features are usually held back on purpose.

## The answer key

Every `.js` file ends with one comment block holding the answers, after all the given wiring — the last thing in the file, so scrolling to it is a deliberate act.

- **One block, at the bottom.** Never an answer beside its stub, and never a second answer block partway down.
- **Group answers by function, in stub order**, each under a heading naming the function: `--- pickWord() ---`, then the lines that complete it.
- **Give the working lines, not prose.** Enough to type in and see it run; a sentence of why only when the line alone would puzzle.
- Keep it in step with the stubs. Renaming a stub, reordering the stubs, or changing a signature means editing the key in the same change.
- **A test file carries its own key, at its own bottom.** Opening `NN.test.ts` must not give away `NN.ts`, and the reverse.

## Each project builds on the last

**Never re-teach what an earlier project already taught.** The learner works the folders in order, so project 03 may assume everything 01 and 02 covered.

- A concept gets one full explanation, in the earliest project that needs it. Later projects name it and point back: "Read `01-calculator/README.md` again for the full story."
- Every README after the first opens its **Good to know** with a `### What you already know` list — one line per carried-over idea, no teaching, plus the pointer to the earlier READMEs.
- Only put an idea in that list if an earlier project genuinely covered it. Listing something as known when it is new is worse than repeating it.
- Explain in full only what is actually new here, or what an earlier project used in its given wiring without ever explaining.
- Same for repeated mechanics — the console, the sound pattern, `render()`. One sentence saying it works as before, then only the part that differs.
- Stub hints follow the same rule. A hint names a method the learner has met; it does not re-introduce it.

Repetition is not kindness here. It buries the one new idea the project exists to teach.

## Hard constraints

These hold everywhere, in every project:

- Relative asset paths throughout — the repo deploys to GitHub Pages from its root on every push to `main`.
- **Single quotes for JavaScript strings** — in the code, and in every code sample the learner copies from: stub hints, answer keys, comments, READMEs. A string holding an apostrophe or a single quote keeps double quotes rather than an escape: `"Dealer's turn"`, `"26px 'Trebuchet MS', sans-serif"`. English quotation in prose stays double too — `means "first in, first out"` quotes a phrase, it does not show a string. HTML attributes and CSS keep their usual double quotes.
- Sounds follow one pattern: build the `Audio` object once, reuse it, rewind with `currentTime = 0`, and swallow the pre-interaction autoplay refusal with `.catch(() => {})`.
- No framework beyond the one library a project's `PRODUCT.md` names.

These hold for **projects 01–16 only**, and three cutovers lift them in turn:

| Constraint | Holds through | Lifted by |
|---|---|---|
| One `.js` file per project | 13 | **14**, many files |
| No build step, no dependencies, no network | 14 | **15**, a server; **17**, npm and a bundler |
| Works by double-clicking the HTML | 16 | **17**, a dev server |
| Classic scripts only — no `import`/`export`, no `type="module"` | 16 | **17**, a build step |

Never lift a constraint early. A library that arrives before its cutover drags the whole toolchain forward — vendor the file next to the HTML instead, as project 9 does with `phaser.min.js`.

`ROADMAP.md` holds the full sequence and what each cutover costs.

## Tests

Tests exist in projects 18 to 22 only. Every later project may have them; no project must.

- **Vitest**, run with `npm test`. It needs no configuration.
- **Pure logic only.** Test functions that take values and return values. Never the DOM, never Phaser, never drawing.
- **Three or four finished tests, two stubs.** The stubs are the learner's work, the same as any other stub.
- **The learner writes the test stub before the function it tests.** The implementation stub's hint says so: `Write its test first — see NN.test.ts`.

Tests are a scaffold like any other. Filling in a test stub is the learner's work, so leave it unwritten.

## Verifying a change

Playwright drives a real browser and is the way to check any page change. Load the page from a `file://` URL, then assert on console errors, element geometry for layout claims, and a full play-through for logic.

Hangman established a convention worth copying: demo states behind a URL hash — `#demo`, `#demo-win`, `#demo-lose` — that make the finished look inspectable while the stubs are still empty. They work by standing in for unfilled stubs at runtime, so a demo that renders blank usually means a stub the demo forgot to cover.

## Adding a project

Sequence numbers are part of the folder name and the learning path.

**A number never changes once its folder exists.** Later READMEs point back at earlier projects by folder name, and those pointers accumulate — renaming a folder breaks all of them. A project inserted between 07 and 08 takes a letter suffix: `07b-something`. It still sorts correctly.

A new project means: the `NN-name/` folder with the seven files above, a card in `showcase.html` (`Ready` with a link, or a disabled `Coming Soon` article), and an entry in `ROADMAP.md` and the root `README.md`.

`index.html` only redirects to `showcase.html`.
